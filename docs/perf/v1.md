# v1 performance (SPEC 10)

Measured 2026-09-30 for tickets 11, 15, 17, 19 and 20, and again on
2026-10-01 after tickets 21 to 24 (see the last section). Release build with `devtools`,
against the fake provider in `tools/demo/` padded to 50,000 channels (229
categories, about 350k programmes, about 24k distinct logo URLs).

Machine: Ryzen 5 3600, GTX 970 on the proprietary driver, Umbriel, two
1920x1080 outputs: HDMI-A-1 at 60 Hz and DP-1 at 144 Hz. The window was
tiled full-screen (1900x1060) and the desktop was in normal use.

## Results

| Metric | Budget | Measured | |
|---|---|---|---|
| Launch to first frame, cached data | < 300 ms | median 188 ms, 167 to 247 ms over 20 launches | met |
| Search, per keystroke | < 16 ms | 1.8 to 7.9 ms | met |
| List scrolling, 60 Hz | holds 60 | 59.9 to 60.2 fps | met |
| List scrolling, 144 Hz | holds 144 | median 141 to 142 fps in the stress test | accepted, see Scrolling |
| Idle CPU | ~0 | 0 ms of CPU time in 30 s | met |
| Idle memory | < 200 MB | 139 to 146 MB RSS | met |
| Channel switch | < 50 ms | under 1 ms | met |

### Launch

Timed from the top of `main` to the end of the first render (`first frame`
in the debug log). Exec and dynamic linking come before that and are not
counted.

With femtovg as published, launch was over budget: median 290 ms, 239 to
371 ms, 6 of 20 launches over. Where that went: about 10 ms to read config
and open the database, 60 ms to create the window (fonts), 60 to 80 ms for
the GPU driver to set up, and 110 to 180 ms to render the first frame. The
category read (5 ms) and the search index (50 to 100 ms, on a worker thread)
do not hold it up.

About 100 ms of that first render was glyph hinting. femtovg 0.27.0 makes a
new swash cache key for every glyph it rasterises, so swash rebuilds the
font's hinting state per glyph instead of once per font and size. Slint
1.18.1 and femtovg 0.27.0 are the latest releases, so the fix is carried in
a vendored copy (`vendor/README.md`, ticket 15). The rendered text is
pixel-identical.

### Search

The filter alone, from the debug log, typing three queries in All. The
slowest keystrokes (5 to 8 ms) are the first one or two letters and queries
that match most of the list; the rest take 2 to 3 ms. The frame that shows
the result renders in 2 to 5 ms.

### Scrolling

`VIDICON_FPS=1` selects the next row every frame, so the list scrolls one row
per frame and the detail panel is refilled every frame. That is harsher than
any real input: a held key repeats a few dozen times a second, and wheel or
drag scrolling does not move the selection.

| Output | Logo cache | fps per second, min / median / max | render p50 | render max |
|---|---|---|---|---|
| 60 Hz | warm | 59.9 / 60.0 / 60.2 | 3.6 ms | 7.9 ms |
| 60 Hz | cold | 59.9 / 60.0 / 60.1 | 3.6 ms | 6.8 ms |
| 144 Hz | warm | 130.0 / 141.3 / 144.1 | 2.4 ms | 5.8 ms |
| 144 Hz | cold | 139.9 / 142.1 / 144.5 | 2.4 ms | 6.4 ms |

Warm means the rows scrolled have their logos in the disk cache, so they
arrive as fast as they are asked for; cold means they are being downloaded
at the SPEC 6.2 rate.

At 144 Hz a frame that takes more than about 4 ms to render misses the
compositor's deadline, and the stress test has a tail of 4 to 6 ms frames.
That tail is the detail panel: the same run without refilling it held 143 to
144 fps, as does the prototype's list (`PROTO_FPS=1` on `prototype/slint`,
measured the same day). Accepted on 2026-09-30 (ticket 16, SPEC 10): no
real input moves the selection on every frame.

Fixed in this pass: a logo arriving for a channel already scrolled past
rebuilt the whole detail panel, recently played and NOW PLAYING. With a warm
cache that cost 10 to 25% of frames (110 to 129 fps at 144 Hz). The detail
panel now waits for one logo at most and only sets the image.

### Idle

Window open on All, nothing playing, after 15 s: no CPU time used in the
next 30 s. RSS 139 to 146 MB, of which 32 MB is the app's own (anonymous)
memory and the rest is mapped libraries, mostly the GPU driver; PSS 80 to
85 MB. After 24 s of the scrolling stress test: 154 to 165 MB (logo images
held, at most 1024).

Once a minute the rows and the detail panel are re-read for the new time
(ticket 17). That blocks the UI thread for about 1.1 ms with 50k channels in
the list and 0.7 ms in a category of 20 (`minute refresh` in the debug log):
telling Slint about a row it has not built costs about 10 ns. The frame that
follows renders in 5 to 7 ms, and about 20 more frames of 1.5 to 3 ms follow
over 150 ms. That length matches the scrollbar animation in Slint's default
widget style; the cause was not confirmed beyond that. In all a tick uses
about 60 ms of CPU time, in All and in a small category alike, and the
longest stall of the event loop measured around one was 18 ms. The 20 ms
first measured in a small category did not repeat.

The first launch with an empty GPU shader cache (`$XDG_CACHE_HOME/nvidia`)
holds about 200 MB while the driver compiles shaders. Later launches do not.

### A–Z order

Ticket 19, All in A–Z (the order is kept, so a launch opens in it):

- Launch to first frame: median 183 ms, 158 to 241 ms over 20 launches.
- Reading All's 50k row keys: 6.6 to 10 ms, the same as in provider order
  (8 to 8.5 ms). The two `name_norm` indexes serve A–Z directly; a store
  test checks the query plan has no sort step.
- Scrolling at 144 Hz, the stress test above: 141.4 / 143.0 / 144.3 fps,
  render p50 2.2 ms, max 6.1 ms.

The indexes cost the channel import: replacing 50k channels takes about
870 ms instead of 400 ms, on the writer, which the UI does not wait for.
Dropping them for the import and rebuilding after took 520 to 620 ms; not
done, as an import runs every 12 h in the background.

### Category allowlist

Ticket 20. All leaves out the channels of hidden categories with one
`NOT IN` over the hidden set, which SQLite builds once per query. Checked
per channel against `category` instead, reading All took 50 to 87 ms and
one launch went over budget. All's two indexes now end in `category_id`, so
the query reads no channel rows, and ties within a number break by
`category_id` before `rowid`: SQLite cannot put `rowid` in an index, and
with `category_id` last the old `num, rowid` order needed a sort step
(28 to 52 ms).

- No rules: reading All's 50k row keys takes 10 to 16 ms (8 to 8.5 ms
  before). Launch to first frame 176 to 240 ms over 6 launches.
- Rules `gen|` and `uk|`, so All shows 49,844 of 50,000 channels, the
  most the filter has to check:
  - Launch to first frame: median 202 ms, 172 to 255 ms over 20 launches.
    Reading All: 15 to 32 ms.
  - Search per keystroke: 2.6 to 8.2 ms over three queries.
  - Scrolling at 144 Hz, provider order: 141.9 / 144.0 / 144.2 fps,
    render p50 2.2 ms, max 5.0 ms. A–Z: 139.6 / 143.6 / 144.4 fps; a first
    run had three seconds at 120 to 136 fps that did not repeat.
- Rule `uk|` alone (34 channels): reading All still scans the index,
  10 to 12 ms.
- A 50k-channel import took as long as before: 2.6 to 2.8 s from the
  categories to the commit, the 2 s request gap (SPEC 6.2) included, both
  before and after.

### Channel name rules

Ticket 25, measured 2026-10-01, same setup. All and each category leave
out the channels a channel rule hides with a second `NOT IN`, over a set
SQLite builds from `channel_hidden`, a partial index holding only hidden
channels. With no rules that set is empty, and All's covering indexes are
unchanged.

- No rules: reading All's 50k row keys 12 to 17 ms, launch to first frame
  195 to 204 ms over 6 launches, as before.
- Rules `summit`, `redwood`, `bluefin` and `halcyon`, so All shows 33,217
  of 50,000 channels (about a third hidden, as on the real provider):
  - Launch to first frame: median 216 ms, 185 to 256 ms over 20
    launches. Reading All: 27 to 50 ms, against 12 to 17 ms without the
    rules; the hidden set is the difference.
  - Search per keystroke: 1.6 to 3.7 ms over three queries.
  - Scrolling at 144 Hz: 137.8 / 141.9 / 144.4 fps, render p50 2.45 ms,
    max 6.5 ms, as this morning.
- Manage mode, on the UI thread (`manage mode read`, `manage filter` in the
  debug log). Opening reads and folds every channel's name once, for the
  rule counts: 63 to 96 ms. An edit re-reads the categories but not the
  names: 29 to 49 ms. A keystroke, counting what the filter would hide as
  a rule: 0.1 to 5 ms. Before keeping the names, every edit took 110 to
  177 ms and every keystroke 11 to 43 ms, mostly the shown channel count
  re-run per key.
- On the writer: applying the rules after an edit takes about 110 ms, and
  about 190 ms of a 50k-channel import, which the UI does not wait for.

### Kept tags

Ticket 26, measured 2026-10-01, same setup. Kept tags set `channel.shown`
like the channel rules, so the lists filter on the same `NOT IN`. The
generated categories now carry a third each `GEN:`, no tag and `ALT|`, so
keeping `gen` hides 16,655 of 50,000 channels and All shows 33,345, about
a third hidden as above.

- Launch to first frame: median 214 ms, 189 to 260 ms over 20 launches.
  Reading All: 26 to 55 ms, as with the channel rules.
- Search per keystroke: 1.3 to 6.5 ms over three queries.
- Scrolling at 144 Hz: 138.9 / 141.9 / 144.1 fps, render p50 2.4 ms, max
  5.6 ms.
- Manage mode: opening 52 to 56 ms, an edit 26 to 53 ms. A keystroke 0.6
  to 6.1 ms, counting live for both the Ctrl+H and the Ctrl+K button: the
  tag of each name in shown categories is read again per key.

### Channel switch

`loadfile sent` in the debug log: under 1 ms after the keypress while mpv
runs. The first play also starts mpv and waits for its IPC socket: 68 to
92 ms with mpv 0.41, which is mpv's own start-up time.

### Catch-up guide window

Catch-up ticket 02, measured 2026-10-02 against the user's provider (not
the demo), on a copy of the real database, release builds, one full
refresh each with the ticket's parent (`main`) and with the ticket.
About 1k channels have an archive.

| | Before | After |
|---|---|---|
| Programmes kept | about 122k | about 135k |
| Of those, ended over 1 h ago | none | about 13k |
| Database | 58 MB | 63 MB |
| EPG request to commit | 3.9 s | 3.8 s |

The time runs from the channel import's commit to the EPG's, so it

### Movie and series lists

VOD ticket 03, measured 2026-10-02 on the demo provider's database padded
with 183k synthetic movies (01's count), release build with `devtools`,
on DP-1 at 144 Hz. Not measured against the real provider.

| | Measured |
|---|---|
| Scrolling All movies, `VIDICON_FPS=1`, 144 Hz | 139.9 to 144.7 fps per second, median 144.0; render p50 1.6 to 2.1 ms, max 6.9 ms |
| Opening All movies, 183k keys, either order | 33 to 63 ms |
| Opening a 20k category | 2 to 5 ms |
| Opening Recently added (200) | 0.4 to 0.6 ms |

Rows are read one at a time by key, as channels are, so a movie list
holds only its keys (about 1.4 MB at 183k). Every order is read from an
index (migration 18; `title_lists_are_read_from_an_index`). Those
indexes cost the import: inserting the 183k synthetic movies took 0.8 s
without the four movie indexes and 2.9 s with them, and the movie table
and its indexes took 26 MB on disk before and 50 MB after (vacuumed;
real names are longer, so expect more). Without the A–Z indexes, All
movies in A–Z order read in about 2.4 times the time (127 against 306
ms in a Python probe, best of 5), so they stay. Not re-measured on the
real provider's import.

### Scoped search

VOD ticket 09, measured 2026-10-03 against the user's real database
(about 58k channels, 17.7k of them shown; 183k movies; 49k series),
release build with `devtools`, keys replayed 30 ms apart. Common English
words as queries, so most keystrokes match thousands of titles: a stress
case.

| | Before the letter sets | After |
|---|---|---|
| Movies' All, per keystroke | 11 to 28 ms | 5 to 16 ms, rare outliers to 18 ms (accepted, SPEC 10) |
| Widened, about 250k names, per keystroke | 10 to 30 ms | 6 to 15 ms |
| Live All, per keystroke | | 0.5 to 2.4 ms |
| Tab: reading each kind's All keys | | 90 to 120 ms, once |
| Resident memory after launch | 152 MB (channel names only) | 163 MB |

A benchmark over the real movie names showed where the time went: nucleo
spends about 140 ns per name even on one it rejects, and a map of
separately allocated names, cold between keystrokes, took two to three
times as long as the same scan warm. Each index now holds its names end
to end by row key with a 64-bit set of the letters and digits in each,
and a name missing one the query needs is skipped before nucleo. Each
scoring thread sorts its own share, and the last sort only merges them.
The slowest keystrokes left are queries of one to five letters that
match 20k to 120k titles, all of which nucleo has to score.

### M3U import

M3U ticket 02, measured 2026-10-22 against the demo provider's
`/playlist.m3u` padded to 50,000 channels (50,003 entries, 11.7 MB, one
entry with no URL), release build with `devtools`. The time is the
import's own log line, from before the request to the commit.

| | Measured |
|---|---|
| Into an empty database | 1.8 to 2.2 s, the body read in 0.65 to 0.69 s |
| Over the 50k stored (`r`) | 2.8 to 3.0 s, the body read in 1.7 to 1.9 s |

The parse keeps up with a local server; over stored channels the
writes slow it, so the body takes longer to drain. Both are about an
Xtream channel import's 2.6 to 2.8 s (Category allowlist above), which
includes the 2 s gap before its list request; a playlist is one
request, with no gap first. Peak heap is covered by
`m3u_import_peak_memory_does_not_scale_with_list_size`: 66.5 KB at 5k
and at 50k entries. `cargo test --release m3u_import_time -- --ignored
--nocapture` times the parse and write alone.

## Reproducing

Set up the throwaway directories as in `tools/demo/README.md`, with the
provider started as `python3 tools/demo/demo_xtream.py 47811 50000`, and
use a release build (`cargo build --release`) in the `vidicon` function.
Run once and wait for `programmes imported` in the log before measuring.

```sh
# Launch: first frame, then exit.
RUST_LOG=vidicon=debug vidicon --screenshot /dev/null 2>&1 | grep 'first frame'

# Search: filter time per keystroke.
RUST_LOG=vidicon=debug vidicon --screenshot /dev/null --keys '/summit<Space>news' 2>&1 | grep 'search "'
# Movies' All, then widened (VOD ticket 09); the jk pairs let the movie index build.
RUST_LOG=vidicon=debug vidicon --screenshot /dev/null \
  --keys "<Tab>$(printf 'jk%.0s' $(seq 60))/the<Space>night<Tab>" 2>&1 | grep -E 'search "|all kinds'

# Scrolling: one line of frame stats per second; `--keys` first, e.g. 'l' for a category.
VIDICON_FPS=1 vidicon

# Channel switch: needs the fake or the real mpv.
RUST_LOG=vidicon=debug vidicon --play --screenshot /dev/null \
  --keys 'jj<Enter>jkjkjkjkjkjkjkjkjkjk j<Enter>jkjkjkjkjkjk' 2>&1 | grep loadfile

# Idle: CPU ticks (fields 14 and 15 of stat) 30 s apart, and memory.
awk '{print $14 + $15}' /proc/$PID/stat
grep -E 'VmRSS|RssAnon' /proc/$PID/status

# Category rules (ticket 20): add them once, then measure as above. Kept
# in the database; the same keys again remove them.
vidicon --screenshot /dev/null --keys 'e gen|<C-Enter><Backspace><Backspace><Backspace><Backspace>uk|<C-Enter>'

# Channel rules (ticket 25): added once like the category rules; the same
# keys again remove them.
vidicon --screenshot /dev/null --keys 'e summit<C-h><Backspace><Backspace><Backspace><Backspace><Backspace><Backspace>redwood<C-h><Backspace><Backspace><Backspace><Backspace><Backspace><Backspace><Backspace>bluefin<C-h><Backspace><Backspace><Backspace><Backspace><Backspace><Backspace><Backspace>halcyon<C-h>'

# Kept tags (ticket 26): keeps gen; the same keys again stop keeping it.
vidicon --screenshot /dev/null --keys 'e gen<C-k>'

# Minute tick: how long the re-read blocks the UI thread. Leave it running.
RUST_LOG=vidicon=debug vidicon 2>&1 | grep 'minute refresh'
```

- Outputs: a window rule puts Vidicon on DP-1. To measure at 60 Hz, focus
  it and run `umbriel msg window-move-to-output-left`.
- The probe's `fps` counts frames rendered; `interval` is the time between
  the ends of consecutive renders, so it jitters with render time even when
  no frame is missed; `render` is the time inside Slint's renderer, before
  the buffer swap.
- Cold logos: delete `$XDG_CACHE_HOME/vidicon/logos` only. A wholly new
  cache directory also empties the GPU shader cache and skews memory.
